# Srez

Self-hosted веб-приложение для одного владельца: учёт биржевых бумаг и крипты, автосбор операций из Т-Инвестиций, несколько портфелей, доходность, выплаты, аналитика. Интерфейс на русском. Разворачивается в Docker на домашнем NAS.

Название сервиса — **Srez** (латиницей, от «срез портфеля»). В коде и UI используй константу `APP_NAME = 'Srez'` из одного места, не хардкодь. Знак — круг с отодвинутым сектором: `design/logo.svg` для меню и экранов входа, `design/logo-icon.svg` для фавикона и иконки приложения. Правила в `docs/08-ui.md`, раздел 2.

## Стек (решения приняты, не менять без согласования)

- Next.js, последняя стабильная версия на момент старта (ветка 16.x или новее), App Router, React Server Components, Server Actions. TypeScript в режиме `strict`.
- SQLite (файл `data/srez.db`, режим WAL) через `better-sqlite3` и Drizzle ORM. Миграции через drizzle-kit, только вперёд.
- Фоновые задачи: отдельный процесс `worker` в том же образе. Очередь — своя, таблица `jobs` в той же базе, расписание по cron-выражениям (`croner`). Redis и pg-boss не используем.
- Аутентификация: Better Auth с плагинами username, two-factor, passkey и адаптером Drizzle.
- Стили: Tailwind CSS v4, токены через CSS-переменные из `docs/08-ui.md`. Примитивы (диалог, селект, меню) на Radix. Графики на Recharts или своём SVG.
- Валидация: Zod на каждой границе (формы, server actions, route handlers, ответы внешних API).
- Деньги и количества: `decimal.js` в коде, `text` (десятичная строка) в базе. Суммирование и сравнение денег только в коде, не в SQL.
- Логи: pino, плюс запись в таблицу `logs`.
- Тесты: Vitest для домена, Playwright для сквозных сценариев.
- Менеджер пакетов: pnpm.

Версии и API библиотек меняются. Перед тем как писать код против Next.js, Better Auth, Drizzle, better-sqlite3 или внешнего API, сверься с актуальной официальной документацией. Если она расходится с `docs/`, скажи об этом и предложи правку документа.

## Команды

Заведи их в фазе 0 и держи этот раздел актуальным.

```
pnpm dev            # web, режим разработки
pnpm worker:dev     # воркер, режим разработки
pnpm db:generate    # сгенерировать миграцию из схемы (src/db/schema)
pnpm db:migrate     # применить миграции к DATABASE_PATH
pnpm test           # юнит-тесты
pnpm test:e2e       # Playwright, проекты desktop (1440) и phone (390)
pnpm check          # typecheck + lint + test, обязателен перед завершением задачи
pnpm build          # next build (standalone) + бандлы worker/migrate/cli в dist/
pnpm cli <команда>  # служебные команды: user:create, user:reset-password
pnpm auth:generate  # таблицы Better Auth из его настроек, затем pnpm db:generate
docker compose up   # всё вместе: web, worker (база — файл ./data/srez.db на томе)
SREZ_PLATFORM=linux/arm64 docker compose up --build   # сборка под Apple Silicon
```

FTS5 и другие вещи, которые drizzle-kit не генерирует, — ручные миграции: `pnpm exec drizzle-kit generate --custom --name <имя>`.

## Жёсткие правила

1. **Никаких float для денег.** Суммы, цены, количества, курсы и доли считаются через `decimal.js` и хранятся в `text` десятичной строкой. `number` допустим только для счётчиков, процентов на выводе и координат графиков.
2. **Журнал операций — источник правды.** Позиции, лоты, снимки и доходность выводятся из операций и могут быть пересчитаны заново. Не храни производное значение, для которого нет пути пересчёта.
3. **Синхронизация идемпотентна.** Повторный импорт той же операции ничего не меняет. Уникальность по `(source_id, external_id)`.
4. **Секреты не утекают.** Токен брокера, ключи, пароли, TOTP-секреты и API-токены не попадают в логи, ответы API, выгрузки, сообщения об ошибках и клиентский бандл. Хранятся зашифрованными, см. `docs/07-auth-security.md`.
5. **Каждая мутация проверяет сессию и валидирует вход через Zod.** Доверять данным из клиента нельзя.
6. **Доменная логика чистая.** Расчёты лежат в `src/domain` как функции без обращения к базе и сети, с юнит-тестами. Эталонные примеры из `docs/04-calculations.md` должны проходить.
7. **Вёрстка по макетам.** Цвета, шрифты, радиусы и отступы берутся только из токенов. Новые цвета и шрифты не добавлять. Числа в макетах условные: не переносить их в код, кроме тестовых фикстур.
8. **Язык.** Тексты интерфейса на русском, собраны в одном модуле. Код, идентификаторы, комментарии, коммиты на английском.
9. **Форматирование чисел.** Только через общие функции форматирования (`docs/08-ui.md`, раздел «Форматы»). Минус — знак «−», десятичный разделитель — запятая.
10. **Время.** В базе UTC (миллисекунды Unix в `integer`). Часовой пояс отображения берётся из настроек.
11. **Не выходить за фазу.** Идеи и находки записывай в `docs/BACKLOG.md`, а не реализуй.

## Когда спрашивать

Остановись и спроси владельца, если:

- нужна зависимость, которой нет в стеке;
- требуется изменить контракт из `docs/03-data-model.md` или `docs/06-api.md`;
- миграция удаляет или необратимо меняет данные;
- требование противоречит макету или другому требованию;
- внешний API ведёт себя не так, как описано в `docs/05-integrations.md`.

Мелкие решения по реализации принимай сам и коротко фиксируй в `docs/PROGRESS.md`.

## Порядок работы

1. Одна фаза из `docs/09-plan.md` за раз, задачи по порядку.
2. Перед фазой составь план и покажи его. После согласования пиши код.
3. Каждая задача заканчивается проходящим `pnpm check` и коммитом в стиле Conventional Commits.
4. После задачи обнови `docs/PROGRESS.md`: что сделано, какие решения приняты, что осталось.
5. Фаза закрыта, когда выполнены её критерии приёмки и владелец подтвердил.

## Определение «готово» для экрана

- Совпадает с макетом на 1440 и 390 пикселей по ширине.
- Есть состояния: загрузка, пусто, ошибка.
- Работает с клавиатуры, у интерактивных элементов видимый фокус.
- Данные приходят с сервера, демо-значений в коде нет.
- Мутации показывают результат и ошибку.
