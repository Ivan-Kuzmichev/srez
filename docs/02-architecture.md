# Архитектура

## 1. Процессы

Один образ, три контейнера:

```
┌────────────┐      ┌────────────┐
│    web     │      │   worker   │
│  Next.js   │      │  очередь   │
│  UI + API  │      │  задачи    │
└─────┬──────┘      └─────┬──────┘
      │                   │
      └────────┬──────────┘
               ▼
        ┌────────────┐
        │   SQLite   │
        │ data/*.db  │
        └────────────┘
```

- **web** отдаёт интерфейс, server actions и `/api/v1`. Во внешние сервисы сам не ходит, кроме проверки токена в мастере первого запуска.
- **worker** выполняет всё долгое и всё по расписанию: синхронизацию, сверку, обновление цен и курсов, ежедневный снимок, начисления, пересчёт позиций, уведомления, чистку логов.
- Общение между ними только через базу: web ставит задачу в очередь, worker пишет результат и прогресс в таблицы, интерфейс их читает.

## 2. Каталоги

```
src/
  app/                    маршруты App Router
    (auth)/               вход, 2FA, пасскей
    (app)/                всё под сессией, общий каркас
    api/auth/[...all]/    обработчик Better Auth
    api/v1/               внешний REST API
  components/
    ui/                   кнопка, поле, селект, карточка, таблица, пилюля
    charts/               линия, столбцы, область, стековая полоса
    shell/                боковое меню, нижняя панель, шапка
    <feature>/            компоненты разделов
  domain/                 чистые расчёты, без базы и сети
    positions.ts lots.ts returns.ts allocation.ts rebalance.ts
    risk.ts bonds.ts accruals.ts reconcile.ts money.ts
  db/
    schema/               таблицы Drizzle
    queries/              чтение для страниц
    mutations/            запись
  integrations/
    tinvest/ prices/ fx/ chains/ telegram/
  jobs/                   обработчики задач и расписание
  server/
    actions/              server actions по разделам
    auth.ts crypto.ts logger.ts settings.ts
  lib/
    format.ts i18n/ru.ts zod/
  cli/                    user:create, user:reset-password, db:backup
worker.ts                 точка входа воркера
design/                   макеты, в сборку не попадают
docs/
```

Правила зависимостей:

- `domain` не импортирует ничего из `db`, `integrations`, `server`, `app`.
- `integrations` не знает о базе: принимает параметры, возвращает проверенные Zod данные.
- `jobs` связывает интеграции, домен и базу.
- Страницы читают через `db/queries`, пишут через `server/actions`.

## 3. Потоки данных

### Синхронизация Т-Инвестиций

1. Расписание или кнопка ставит задачу `sync.tinvest` с `source_id`.
2. Воркер создаёт запись в `sync_runs`, для каждого включённого счёта тянет операции с последней известной даты минус 3 дня.
3. Операции приводятся к внутреннему виду и вставляются с `ON CONFLICT DO NOTHING` по `(source_id, external_id)`.
4. Недостающие инструменты создаются по данным API.
5. Ставятся задачи `positions.recalc` для затронутых счетов и `reconcile.run`.
6. Запись `sync_runs` закрывается: статус, число новых операций, ошибка.

### Пересчёт

`positions.recalc(account_id)` читает все операции счёта по порядку, строит позиции и FIFO-лоты через `domain`, перезаписывает таблицы `positions`, `lots`, `lot_closures` в одной транзакции. Вызывается после любого изменения операций счёта.

### Ежедневный снимок

`snapshot.daily` в заданное время: обновляет цены и курсы, пишет `position_snapshots` на дату, считает начисления по кошелькам, проверяет условия уведомлений. Пропущенные дни достраиваются при старте воркера.

### Чтение

Страницы — серверные компоненты, читают из базы уже посчитанное. Ряды для графиков собираются запросом по `position_snapshots` с учётом правил портфеля. Кэш Next.js для данных пользователя не используется: всё динамическое.

## 4. Числа, валюты, время

- Тип `Money` в `domain/money.ts`: обёртка над `Decimal` с валютой. Сложение разных валют — ошибка.
- В базе количества, цены, суммы и курсы хранятся в `text` десятичной строкой без потери точности (у крипты до 18 знаков после запятой). Агрегаты по деньгам считаются в коде через `decimal.js`, не в SQL. Округление только на выводе.
- Пересчёт в валюту отображения по курсу на дату операции или снимка.
- Все даты в UTC. «День» для снимков и группировок считается в часовом поясе из настроек.

## 5. Конфигурация

Переменные окружения, файл `.env.example` лежит в корне.

| Переменная | Назначение |
|---|---|
| `DATABASE_PATH` | Путь к файлу SQLite, по умолчанию `./data/srez.db` |
| `APP_URL` | Публичный адрес, например `https://invest.home.arpa`. Нужен для кук и пасскеев |
| `APP_SECRET_KEY` | 32 байта в base64. Ключ шифрования секретов в базе |
| `AUTH_SECRET` | Секрет Better Auth |
| `TRUSTED_PROXIES` | Список адресов обратных прокси, которым разрешено передавать `X-Forwarded-For` |
| `TINVEST_PROXY_URL` | Необязательно. HTTP или SOCKS5 прокси только для запросов к Т-Инвестициям |
| `LOG_LEVEL` | Уровень логов по умолчанию до загрузки настроек |
| `TZ` | Часовой пояс контейнера, по умолчанию `UTC` |

Всё, что меняется из интерфейса, лежит в таблице `settings`, а не в окружении.

## 6. Развёртывание

`docker-compose.yml`:

- База — файл SQLite на томе `data`, общем для `web` и `worker`. Режим WAL. Том обязан лежать на локальном диске хоста: по SMB/NFS блокировки SQLite ненадёжны.
- `web`: сборка из `Dockerfile` (multi-stage, `output: 'standalone'`), порт 3000, при старте применяет миграции, healthcheck по `/api/health`.
- `worker`: тот же образ, команда `node worker.js`, стартует после здорового `web` (миграции уже применены).
- Пользователь внутри контейнера не root. Тома только для базы и резервных копий.
- Целевая платформа: `linux/amd64`. NAS слабый: сборку образа лучше делать не на нём.

Сервис рассчитан на работу за обратным прокси с HTTPS. Напрямую в интернет не выставлять.

## 7. Ошибки и логи

- Логгер pino с дочерними логгерами по источникам: `auth`, `api`, `collector`, `prices`, `jobs`, `chains`, `notify`, `web`.
- Каждый HTTP-запрос и каждая задача получают `request_id` или `job_id`, он проходит через все записи.
- Записи идут в stdout и в таблицу `logs` (пакетной вставкой). Срок хранения из настроек, чистка задачей.
- Редактор секретов на уровне логгера: поля `token`, `password`, `secret`, `authorization`, `cookie`, `key` заменяются на `[redacted]` на любой глубине.
- Ошибки внешних API оборачиваются в типизированные классы с кодом, чтобы интерфейс показывал понятный текст, а лог — технический.

## 8. Тестирование

- `domain`: юнит-тесты, включая эталонные примеры из `04-calculations.md`. Покрытие домена не ниже 90 %.
- `integrations`: тесты на записанных ответах (фикстуры), без сети.
- `jobs`: интеграционные тесты на тестовой базе.
- e2e: вход, первый запуск на мок-сервере Т-Инвестиций, ручная операция, создание портфеля, расчёт ребаланса.
- Мок-сервер Т-Инвестиций живёт в `tests/mocks/tinvest` и отдаёт фикстуры по тем же путям, что и настоящий API.
